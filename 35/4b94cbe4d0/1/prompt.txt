## 2. TopologyMaterializer and TopologyRules

### `/src/Intropy.Topology/Building/TopologyMaterializer.cs` (146 lines)
`internal static SystemTopology Materialize(SystemBuilder builder)`. Materialization **never fails** — first-seen wins on identity conflicts so validation sees the whole picture. Pattern for a resource-from-usage:

```csharp
var connectors = new Dictionary&lt;string, ConnectorAccumulator&gt;();
...
Connectors = connectors.OrderBy(c =&gt; c.Key, StringComparer.Ordinal)
    .Select(c =&gt; new ConnectorResource { Name = c.Key, Transport = c.Value.Transport,
        Directions = [.. c.Value.Directions.Order()], UsedBy = [.. c.Value.UsedBy] }).ToArray(),
```
with private accumulator classes holding `SortedSet&lt;string&gt; UsedBy` (`StringComparer.Ordinal`) and the first-seen identity:
```csharp
private static ConnectorAccumulator AccumulateConnector(dict, ConnectorRef connector, ConnectorDirection direction)
{
    if (!connectors.TryGetValue(connector.Name, out var accumulator))
    {   // First-seen wins on identity; conflicting declarations are reported by validation.
        accumulator = new ConnectorAccumulator(connector.Transport);
        connectors[connector.Name] = accumulator;
    }
    accumulator.Directions.Add(direction);
    return accumulator;
}
```
Per-component edge lists are deduplicated in the component loop (`seenConnectorEdges` HashSet). A `ServiceResource` would slot in as a third dictionary + accumulator + ordered projection; determinism (declaration order for components, `Ordinal` sort for resources) is asserted by the snapshot test.

## 3. Aspire backend — `/src/Intropy.Topology.Aspire/`

Files: `IntropyAspire.cs` (333), `Scheduling.cs` (249), `SidecarRecovery.cs` (149), `ComponentOverlay.cs` (90), `TcpReadyHealthCheck.cs` (73), `ProjectConvention.cs` (33), `README.md` (stale — still documents `IDevProfile`/Microcks/profiles removed by ADR 0009).

### What it creates today
`IntropyAspire.RunAsync(Assembly, string[])`: discover → `TopologyGenerator.Generate(...).WriteTo(tempRoot)` → `Apply(builder, topology, generatedRoot)` → `app.RunAsync()`.

`internal static void Apply(IDistributedApplicationBuilder builder, SystemTopology topology, string generatedRoot)` — the single translate method, ~130 lines, is where a shared service would be added:

1. **One backend container, hard-coded**:
```csharp
internal const int RabbitMqPort = 5672;
var rabbitmq = builder.AddContainer("rabbitmq", "docker.io/library/rabbitmq", "4")
    .WithEndpoint(port: RabbitMqPort, targetPort: RabbitMqPort);
WithTcpReadiness(builder, rabbitmq, RabbitMqPort);
var backends = new List&lt;IResourceBuilder&lt;IResource&gt;&gt; { rabbitmq };
var backendProbes = new List&lt;TcpReadyHealthCheck&gt; { new("localhost", RabbitMqPort) };
```
Deliberately `AddContainer`, **not** `AddRabbitMQ` — the generated YAML speaks fixed `guest/guest` on `localhost:5672`, while `AddRabbitMQ` injects generated credentials (ADR 0005 amended). Same reasoning previously applied to Redis. This is the key precedent: **new shared services should be plain containers on fixed host ports, because generation runs before the run and bakes the endpoint into YAML.** `backends`/`backendProbes` are *already lists* — adding platform-service containers to them is the minimal-diff path.

2. **Three layers of startup ordering** (no `WaitFor` on sidecars is possible):
   - `resource.WaitFor(backend)` and `sidecar.WaitFor(backend)` inside `Wire&lt;T&gt;`;
   - a global `BeforeResourceStartedEvent` hook gating every `*-dapr-cli` resource on all `backendProbes` (up to 3 min) — necessary because the Dapr toolkit materializes each sidecar as a separate executable resource that carries no wait annotations;
   - publisher→subscriber precedence derived from topics.
```csharp
builder.Eventing.Subscribe&lt;BeforeResourceStartedEvent&gt;(async (evt, ct) =&gt; {
    if (!evt.Resource.Name.EndsWith("-dapr-cli", StringComparison.Ordinal)) return;
    foreach (var probe in backendProbes) await probe.WaitUntilReadyAsync(TimeSpan.FromMinutes(3), ct);
    if (sidecarWaits.TryGetValue(evt.Resource.Name, out var subscriberSidecars)) { /* WaitForResourceAsync(Running) */ }
});
```

3. **Per component**: `ComponentOverlay.Stage(...)` → `ProjectConvention.Resolve(...)` (throws with "No project found for these components by folder convention" when missing) → `builder.AddProject(name, path)` → `WithHttpEndpoint()` **only when `Schedule is null`** → `Wire(...)`:
```csharp
private static void Wire&lt;T&gt;(IResourceBuilder&lt;T&gt; resource, ComponentModel component, string resourcesPath,
    string configDir, IReadOnlyList&lt;IResourceBuilder&lt;IResource&gt;&gt; backends)
    where T : IResourceWithEnvironment, IResourceWithWaitSupport
{
    resource.WithDaprSidecar(sidecar =&gt; {
            sidecar.WithOptions(new DaprSidecarOptions { AppId = component.Name, ResourcesPaths = [resourcesPath] });
            foreach (var backend in backends) sidecar.WaitFor(backend);
        })
        .WithEnvironment("INTROPY__COMPONENT", component.Name)
        .WithEnvironment("INTROPY__CONFIG", Path.Combine(configDir, $"{component.Name}.intropy.json"));
    foreach (var backend in backends) resource.WaitFor(backend);
}
```
Note `backends` is applied to **every** component uniformly — a per-component service dependency would need this to become per-component (`component.Services` → the subset of resources to `WaitFor`), which is the main structural change the feature implies. There is **no `AddConnectionString`, no `WithReference`, no env-var injection other than the two `INTROPY__*` variables** anywhere in the repo.

4. **Subscriber-first ordering**: `SubscriberPrecedence(topology)` (publisher → all subscribers of its topics, self-loops skipped) + `HasCycle` DFS; on a cycle it prints to stderr and skips ordering entirely rather than deadlocking. `waiters[name] = dep =&gt; project.WaitFor(dep)` and `sidecarWaits["&lt;pub&gt;-dapr-cli"] = ["&lt;sub&gt;-dapr-cli", ...]`.

5. **`RegisterScheduler`** (only when some component has `Schedule != null`) and **`RegisterDaprSidecarRecovery`** (always) register hosted services via `builder.Services` (`TryAddSingleton&lt;TimeProvider&gt;`, `IResourceLifecycle`, `IResourceStateMonitor`, `IBackendReadiness`).

6. `AddRunNowCommand` — dashboard `WithCommand("intropy-run-now", ...)` resolving `ComponentScheduler` from `context.ServiceProvider`.

### `Scheduling.cs`
- `internal sealed record ScheduledComponent(string Name, string Cron)`
- `internal static class ScheduleTickPlanner.NextOccurrence(string cron, DateTimeOffset after, TimeZoneInfo zone)` (Cronos)
- `internal interface IResourceLifecycle { WatchAsync; IsStartable(string); ExecuteAsync(name, command, ct); WaitUntilRunningAsync(name, timeout, ct) }` + `AspireResourceLifecycle` over `ResourceCommandService`/`ResourceNotificationService` — the testability seam pattern to copy for any new runtime behavior.
- `internal sealed class ComponentScheduler(IReadOnlyList&lt;ScheduledComponent&gt;, IResourceLifecycle, TimeProvider, ILogger) : BackgroundService` — per-component cron loop; `TriggerAsync` gates on a per-component `SemaphoreSlim` (skip on overlap = `concurrencyPolicy: Forbid`), starts `"&lt;component&gt;-dapr-cli"` first and waits for Running (3 min), then the app; `Start` with `Restart` fallback.

### `ComponentOverlay.cs`
`public static string Stage(string appHostDirectory, string componentName, string generatedComponentsDir)` → `&lt;appHost&gt;/obj/dapr-components/&lt;component&gt;/`, wiped and rebuilt each start. Local `&lt;integration&gt;/local/dapr-components/*.y[a]ml` are copied first, then generated files overlay **by top-level `metadata.name`** (`internal static string? MetadataName(string yaml)` — only the unindented `metadata:` block qualifies). Every component gets its own directory (asserted in `IntropyAspireTests.REDACTED`). If a shared service materializes a Dapr component (state store, lock, secret store), this is the mechanism that would scope it per component — and generation would need to emit only the components a given component may see, or rely on Dapr `scopes` as pub/sub and bindings do today.

### `SidecarRecovery.cs`, `TcpReadyHealthCheck.cs`
`DaprSidecarRecovery : BackgroundService` restarts `*-dapr-cli` sidecars that die during component init (max 3 attempts, waits for `IBackendReadiness` first) — because **daprd treats a failed component init as fatal**, which is precisely the risk when adding another backend a sidecar dials. `TcpReadyHealthCheck(host, port)` implements both `IHealthCheck` and `IBackendReadiness`; it requires the connection to survive a 750 ms read window (Docker Desktop's port proxy accepts early). Any new platform-service container should get a probe here and be added to `backendProbes`.

## 6. Existing mentions of platform service / infrastructure / dependency

**The feature existed and was removed** — `/docs/decisions/0004-edges-over-triggers.md` is the primary design record:

- §Interface model table, line 47: `| Service | component ↔ external platform svc | none (external) | sync |` — i.e. a platform service was modeled as a *fourth interface kind* alongside Topic / API / Connector, external (no in-system provider), synchronous.
- §PoC lean pass (2026-07-21), lines 65–77:
```
- **Platform services**: `ServiceRef`, `UseService`, `.Uses`, `ServiceResource`,
  `ServiceUseEdge`, `SystemTopology.Services`, and diagnostics `ITP301`/`ITP402`.
```

# Implementation Plan: System-Level Platform Services (declared containers, Aspire startup gating)

## 0. Design decisions (with justification)

**D1 — Image string embeds the tag** (`Service.Container("docker.io/library/redis:7", 6379)`), no separate `tag` parameter.
- The core model is backend-agnostic and dependency-free; the single Docker image reference (`name[:tag]`) is the tool-neutral form every future consumer uses verbatim (Kubernetes `image:`, docker compose). Aspire's `(name, image, tag)` split is an Aspire detail, so the split belongs in the Aspire package: last `:` after the last `/` (handles `localhost:5000/img`), no colon → `AddContainer(name, image)` (Aspire defaults to `latest`). Digest (`@sha256`) refs are out of scope — document.

**D2 — Builder method is `UsesService(ServiceRef)`, returning `void`.**
- `Add*` on `SystemBuilder` has an established meaning: "declare a component block, get its block builder back" (CLAUDE.md "Key Concepts"). A service is not a component and yields no builder, so `AddService` would break that contract. `UsesService` also echoes the historical `UseService` (ADR 0004 PoC lean pass) in the DSL's present-tense edge style (`Publishes`, `Subscribes`). Returns `void` — the SystemHost declaration style is statements, and no chaining need exists (minimality).

**D3 — Diagnostic codes: mint ITP108 for the identity conflict, revive ITP402 for the name collision, permanently retire ITP301.**
- **ITP402 (revived)**: its old meaning per ADR 0004 was exactly the platform-service name collision. It was removed *with* its feature, never retired-with-prejudice (it's absent from both retired lists). Reviving it with the same meaning is continuity, not reuse.
- **ITP301 (retire permanently)**: its old meaning ("service declared but no component `.Uses` it") is predicated on the per-component edge the user explicitly excluded. With system-level declaration there is no usage to check — the rule is meaningless, and its code must be added to the retired list so it is never repurposed.
- **ITP108 (new)**: "same service name, two different definitions" is a *resource identity conflict*, the ITP1xx band (103 topic contract, 104 connector transport). 105–107 are retired, so 108 is the next free code. The old feature had no such rule (it used a registry, not refs), so no old code exists to revive.
- All three decisions get recorded in ADR 0011, the `TopologyRules` retired-codes comment, and `docs/concepts/validation.md`.

**D4 — `graph` shows services, gated on `Count &gt; 0`.**
- `graph` is the human inspection surface ("what runs"); a declared container is part of that. `DisplayModel` already omits empty collections (`connectors` precedent at `IntropyGenerate.cs:76`), so systems without services print byte-identical output — the constraint in the scope decision holds by construction.

**D5 — `rabbitmq` reservation enforced in the new ITP402 rule, for services only.**
- A service named `rabbitmq` is a guaranteed F5 failure (Aspire resource names share one namespace with the hard-coded broker at `IntropyAspire.cs:65`). Catching it at `Build()`/`check` beats a DCP crash. A *component* named `rabbitmq` has the same problem today — that pre-existing gap stays out of scope (flagged below) to keep this change service-shaped.

/// A shared platform service the system depends on (e.g. an idempotency store).
public sealed record ServiceRef
{
    public string Name { get; }              // DNS-1123 label (becomes the Aspire resource name)
    public Service Service { get; }
    public static ServiceRef Define([ConstantExpected] string name, Service service);
    // private ctor; Define does NameRules.RequireLabel(name) + ArgumentNullException.ThrowIfNull(service)
}

/// What a platform service materializes as — mirrors Transport's polymorphism.
[JsonPolymorphic(TypeDiscriminatorPropertyName = "$service")]
[JsonDerivedType(typeof(ContainerService), "container")]
public abstract record Service
{
    private protected Service() { }
    /// An arbitrary container on a fixed host port. Image may embed a tag ("redis:7"); no tag means latest.
    public static Service Container([ConstantExpected] string image, int port) =&gt; new ContainerService(image, port);
}

public sealed record ContainerService : Service
{
    public string Image { get; }   // full reference, tag optional; digests unsupported
    public int Port { get; }       // fixed host port == container port (generate-before-run constraint)
    public ContainerService(string image, int port)  // public ctor: STJ polymorphic deserialization, FileTransport precedent
    // guards: ThrowIfNullOrWhiteSpace(image); ArgumentOutOfRangeException for port outside 1..65535
}

## Risks &amp; flags

- **Image parsing**: digest references and internal-port≠host-port containers unsupported — documented in `Service.Container` XML docs and ADR 0011.
- **`Uses` naming headroom**: if a per-component edge ever returns (ADR 0004's `.Uses`), system-level `UsesService` does not collide with it — no reserved-name conflict.
